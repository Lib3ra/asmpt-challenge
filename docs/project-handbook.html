A-01

Pflichtanforderungen der Challenge

  • PflichtPlattformunabhängige C#-Anwendung zur Verwaltung von Orders in einer SMT-Fertigung.
  • PflichtCRUD für Orders, Boards und Components.
  • PflichtMany-to-many: Order ↔ Board („one or more“ Boards pro Order, Board in „one or multiple“ Orders) und Board ↔ Component („one or more“ Components pro Board, Component auf „one or more“ Boards).
  • PflichtAttribute: Order (Name, Description, Order Date), Board (Name, Description, Length, Width), Component (Name, Description, Quantity). IDs, Fremdschlüssel und Referenzlisten dürfen ergänzt werden.
  • PflichtErstellen, Bearbeiten, Suchen und Entfernen von einem oder mehreren Components, Boards und Orders.
  • PflichtDownload eines Orders, der die Übergabe an eine Produktionslinie simuliert.
  • PflichtSerialisierung nach JSON; Persistenz mit frei wählbarer Technologie.
  • PflichtLogging relevanter Aktionen und Fehler mit einem verbreiteten Framework.
  • PflichtOOP-Prinzipien (SOLID, DRY), Standard-Entwurfsmuster, Unit-Test für mindestens eine repräsentative Methode.
  • EmpfohlenÜbersicht der modellierten Klassen und der Architektur für die Präsentation im Team („would be beneficial“).
A-02

Optionale Anforderungen, die wir umsetzen

  • OptionalVersion Control: GitHub, kleine Branches, reviewbare PRs. Repository zum Abschluss für Reviewer freigeben.
  • OptionalCI: GitHub Actions baut und testet automatisch und erstellt auf main ein Docker-Image-Artefakt mit Commit-SHA als Tag.
  • OptionalWeb Interface: React-UI über eine ASP.NET Core Web API mit CRUD für alle drei Entitäten.
  • OptionalPersistenz über Neustarts: SQLite mit EF Core, Docker Named Volume auf /data.
  • OptionalContainerisierung: mehrstufiges Dockerfile, Docker Compose. API, Datenbank (SQLite-Datei) und Frontend in einem Container.
A-03

Bewusste Abweichungen

  • AusgelassenCloud-Deployment (Teil der optionalen CI/CD-Anforderung): kein Azure, kein Neon, kein Registry-Push. Die Pipeline endet beim herunterladbaren Image-Artefakt.
  • AusgelassenLogin und Authentifizierung (Teil der optionalen Web-Interface-Anforderung, „accessible via login“). Die UI ist ohne Anmeldung erreichbar.
  • Eingeschränkt„Runnable locally and in the cloud“: Das Image ist cloud-tauglich gebaut (non-root, Konfiguration über Umgebungsvariablen), wird aber nur lokal betrieben und geprüft.
  • Eingeschränkt„Build on each commit“: CI läuft bei Pull Requests und Pushes auf main. Commits auf Feature-Branches werden über den offenen PR gebaut.
A-04

Offene fachliche Fragen

Werden beim jeweiligen Feature gemeinsam entschieden und hier mit Datum nachgetragen.

  • PR 4 / 5Mindestkardinalität: Die Challenge schreibt „one or more“. Muss ein Order beim Speichern mindestens ein Board haben, ein Board mindestens einen Component? Oder sind leere Zuordnungen zulässig, etwa als Entwurf?
  • PR 4 / 5Löschverhalten bei bestehenden Zuordnungen: Sperre, Kaskade oder Entfernen nur der Verknüpfung.
  • PR 3–5„One or more“ bei Aktionen: Sammeloperationen für Erstellen, Bearbeiten, Suchen und Entfernen. Umfang, API-Form und Verhalten bei Teilfehlern sind offen.
  • PR 3Suche: Welche Felder werden durchsucht (Name, Description), mit welcher Logik (enthält, Groß-/Kleinschreibung)?
  • PR 3Validierung: Pflichtfelder, Längen, Wertebereich von Quantity (zum Beispiel 0 oder ganzzahlig größer 0).
  • PR 4Einheit von Length und Width (in der SMT-Praxis üblich: Millimeter) und Datentyp (ganzzahlig oder Dezimal).
  • PR 5Order Date: reines Datum oder Zeitpunkt; Vorgabe beim Anlegen.
  • PR 6JSON-Struktur des Produktionsdownloads und Dateiname.

Hinweise zum Prompt im Vergleich zur Challenge

Quantity: Die Challenge legt Quantity an den Component, ohne die Bedeutung zu definieren. „Anzahl Exemplare pro Board“ ist unsere Interpretation. Wie gefordert bleibt Quantity am Component, auch wenn derselbe Component auf mehreren Boards liegt. Diese Interpretation sollten wir in der Präsentation ausdrücklich nennen.

„One or more“ betrifft alle vier Aktionen, nicht nur das Löschen. Der Prompt berücksichtigt das, legt den Umfang aber zu Recht noch nicht fest.

Darüber hinaus widerspricht der Prompt der Challenge nicht und übersieht keine Pflichtanforderung.

T-02

Code-Konventionen

Verbindliche Fassung im Repository: CLAUDE.md. Diese Übersicht fasst sie zusammen; Änderungen laufen über einen PR an CLAUDE.md.

Backend

  • VorschlagGemeinsame Einstellungen in Directory.Build.props: Nullable aktiviert, Warnungen als Fehler, Implicit Usings.
  • Vorschlag.editorconfig als einzige Stilquelle: 4 Leerzeichen in C#, 2 in TS/JSON/YAML, file-scoped Namespaces, LF.
  • VorschlagEin Feature pro Ordner (Features/Components mit Endpunkten, DTOs und Service). Endpunkte per Extension-Methode MapComponentEndpoints() registrieren.
  • VorschlagEntitäten nie direkt über die API ausgeben, sondern über Request- und Response-DTOs als record.
  • VorschlagStrukturiertes Logging mit Platzhaltern ("Created component {ComponentId}"), keine String-Interpolation.
  • Vorschlagdotnet format --verify-no-changes muss lokal sauber durchlaufen; Aufnahme in CI bei Bedarf.
  • VorschlagTestnamen im Stil Methode_Situation_Erwartung; Kommentare // Arrange, // Act, // Assert in jedem Test; NUnit-Constraint-Modell (Assert.That), mehrere Prüfungen in Assert.EnterMultipleScope().

Frontend

  • VorschlagLinting mit ESLint (Flat Config in eslint.config.js): JS- und typescript-eslint-Empfehlungen sowie die React-Hooks- und React-Refresh-Regeln. npm run lint, npm run typecheck und npm run build müssen in CI grün sein.
  • VorschlagAPI-Zugriffe gebündelt in src/api/; Komponenten rufen fetch nicht direkt auf.
  • VorschlagZunächst keine UI-Bibliothek und kein globaler State-Manager; erst bei konkretem Bedarf einführen.

Git

  • FestgelegtKein direkter Commit auf main; ein Branch pro PR; PRs werden nur von dir gemergt.
  • VorschlagCode, Kommentare, Commits und README auf Englisch; Projekt-Handbuch und Abstimmung auf Deutsch.
  • VorschlagBranch-Namen feat/…, chore/…, docs/…; Commit-Nachrichten im Imperativ, englisch, im Conventional-Commits-Stil.
