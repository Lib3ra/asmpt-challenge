A-01

Mandatory requirements

  • MandatoryPlatform-independent C# application for managing orders in an SMT manufacturing environment.
  • MandatoryCRUD for Orders, Boards and Components.
  • MandatoryMany-to-many: Order ↔ Board (“one or more” boards per order, a board in “one or multiple” orders) and Board ↔ Component (“one or more” components per board, a component on “one or more” boards).
  • MandatoryAttributes: Order (Name, Description, Order Date), Board (Name, Description, Length, Width), Component (Name, Description, Quantity). IDs, foreign keys and reference lists may be added.
  • MandatoryCreate, edit, search and remove one or more components, boards and orders.
  • MandatoryDownload an order, simulating the hand-over to a production line.
  • MandatorySerialize data to JSON; persist it with a technology of our choice.
  • MandatoryLog relevant actions and errors with a commonly adopted framework.
  • MandatoryOOP principles (SOLID, DRY), standard design patterns, a unit test for at least one representative method.
  • RecommendedOutline of the modelled classes and the architecture for the team presentation (“would be beneficial”).
A-02

Optional requirements we implement

  • OptionalVersion control: GitHub, small branches, reviewable PRs. Repository made accessible to reviewers at the end.
  • OptionalCI: GitHub Actions builds and tests automatically and, on main, produces a Docker image artifact tagged with the commit SHA.
  • OptionalWeb interface: React UI on top of an ASP.NET Core Web API with CRUD for all three entities.
  • OptionalPersistence between restarts: SQLite via EF Core, Docker named volume mounted at /data.
  • OptionalContainerization: multi-stage Dockerfile and Docker Compose. API, database (SQLite file) and frontend in one container.
A-03

Deliberate deviations

  • OmittedCloud deployment (part of the optional CI/CD requirement): no Azure, no Neon, no registry push. The pipeline ends with a downloadable image artifact.
  • OmittedLogin and authentication (part of the optional web interface requirement, “accessible via login”). The UI is reachable without signing in.
  • Limited“Runnable locally and in the cloud”: the image follows common container practice (non-root, configuration via environment variables) but was only run and verified locally. A cloud run would also need storage that suits SQLite: a single instance with a local or block volume, because network file shares can break SQLite's file locking.
  • Limited“One or more” when creating boards and orders: only components can be created several at a time. Boards and orders are created one at a time, because each needs its own set of links. Deleting works in bulk for all three.
  • Limited“Build on each commit”: CI runs on pull requests and pushes to main. Commits on feature branches are built through their open PR.
A-04

Domain rules

Decided together on 2026-10-24 before feature work (PR 3). Each rule names the PR that implements it.

  • AllValidation: Name required, trimmed, not blank, max 256 characters. Description optional, trimmed, max 2000. Errors are returned as a standard 400 validation problem (field → messages) and shown next to the form fields.
  • AllUnique names per entity type, case-insensitive. A duplicate is rejected with a clear message. SQLite folds case for ASCII letters only, which is sufficient for technical names.
  • AllBulk operations: delete accepts one or more records for all three entities; create accepts one or more records for components only (boards and orders are created one at a time with their links). Bulk operations take one or more records and run all-or-nothing in one transaction; on failure nothing is saved and every failing item is reported (request rules first; name and link checks against the database follow once those pass). Editing works on one record at a time. Search returns one or more results by nature.
  • AllSearch: case-insensitive “contains” on Name. Each list page has its own name filter; a global search box returns matches grouped by Orders, Boards and Components and can be narrowed to one type. The global search needs a term; clicking a result opens the list page filtered by that name.
  • PR 4Quantity: integer, 1 to 10,000 copies per board.
  • PR 5Length and Width: millimetres as decimal with two places (0.01 mm), greater than 0 and at most 1,000 mm. Named lengthMm / widthMm in the API.
  • PR 6Order Date: date only (2026-10-24), prefilled with today, editable.
  • PR 5 / 6At least one link, enforced on every save: a board always has at least one component, an order at least one board. They are created together with their links, and removing the last link is rejected.
  • PR 5 / 6Delete while in use is blocked: a component used on a board, or a board used in an order, cannot be deleted; the API answers 409 Conflict with a message naming where it is used. In a bulk delete, one blocked record blocks the whole request. Orders can always be deleted, which removes their board links.
  • PR 9Production download: nested JSON order → boards → components plus exportedAt (UTC timestamp of the hand-over); file name order-<id>-<name>.json with a sanitized, lower-case name. A pure export: logged, no status change, the order stays editable.
  • TechCancellationToken stays in endpoints and repositories.

Notes on our brief compared with the challenge

Quantity: the challenge puts Quantity on Component without defining its meaning. “Copies of this component per board” is our interpretation. As required, Quantity stays on Component even when the same component sits on several boards. We should state this interpretation explicitly in the presentation.

“One or more” applies to all four actions. Our reading: creating and removing several records at once are real use cases (entering a component list, cleaning up), so both get bulk operations. Bulk delete exists for all three entities; bulk create only for components, which are entered in lists, while boards and orders are created one at a time with their links (decided 2026-10-24, a deliberate narrowing of “one or more” for creating boards and orders). “Editing one or more” is covered by editing records individually; a mass edit would apply the same value to many records, which has no clear use in this domain. “Searching” returns one or more results by nature. If asked, this is our argument.

Otherwise our brief neither contradicts the challenge nor misses a mandatory requirement.

T-02

Code conventions

The binding version lives in the repository: CLAUDE.md. This overview summarizes it; changes go through a PR to CLAUDE.md.

Backend

  • DecidedShared settings in Directory.Build.props: nullable enabled, warnings as errors, implicit usings.
  • Decided.editorconfig as the single style source: 4 spaces in C#, 2 in TS/JSON/YAML, file-scoped namespaces, LF.
  • DecidedOne folder per feature (Features/Components with entity, endpoints, DTOs and repository). Endpoints registered via an extension method such as MapComponentEndpoints().
  • DecidedEndpoints contain no database code; data access goes through one repository per aggregate. No controller, processor or service layers.
  • DecidedEntity mapping and seed data configured centrally in AppDbContext.OnModelCreating.
  • DecidedExplicit types instead of var, enforced at build time (IDE0008 with EnforceCodeStyleInBuild).
  • DecidedEntities are never exposed by the API; request and response DTOs are declared as record.
  • DecidedStructured logging with message templates ("Created component {ComponentId}"), no string interpolation.
  • Decideddotnet format --verify-no-changes must pass; CI checks it in the backend job.
  • DecidedTest names Method_Situation_ExpectedResult; // Arrange, // Act, // Assert comments in every test; NUnit constraint model (Assert.That), related checks grouped in Assert.EnterMultipleScope().

Frontend

  • DecidedLinting with ESLint (flat config in eslint.config.js): JS and typescript-eslint recommendations plus the React Hooks and React Refresh rules. npm run lint, npm run typecheck and npm run build must pass in CI.
  • DecidedAll API calls live in src/api/; components never call fetch directly.
  • DecidedNo UI library and no global state manager until there is a concrete need.

Git and language

  • DecidedNo direct commits to main; one branch per PR; PRs are merged by the project owner only.
  • DecidedEverything in English: code, comments, commits, README, CLAUDE.md, this handbook and project discussions.
  • DecidedBranch names feat/…, chore/…, docs/…, fix/…; commit messages in imperative mood with a short subject line.
