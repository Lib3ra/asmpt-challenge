A-01

Mandatory requirements

  • MandatoryPlatform-independent C# application for managing orders in an SMT manufacturing environment.
  • MandatoryCRUD for Orders, Boards and Components.
  • MandatoryMany-to-many: Order ↔ Board (“one or more” boards per order, a board in “one or multiple” orders) and Board ↔ Component (“one or more” components per board, a component on “one or more” boards).
  • MandatoryAttributes: Order (Name, Description, Order Date), Board (Name, Description, Length, Width), Component (Name, Description, Quantity). IDs, foreign keys and reference lists may be added.
  • MandatoryCreate, edit, search and remove one or more components, boards and orders.
  • MandatoryDownload an order, simulating the hand-over to a production line.
  • MandatorySerialize data to JSON; persist it with a technology of our choice.
  • MandatoryLog relevant actions and errors with a commonly adopted framework.
  • MandatoryOOP principles (SOLID, DRY), standard design patterns, a unit test for at least one representative method.
  • RecommendedOutline of the modelled classes and the architecture for the team presentation (“would be beneficial”).
A-02

Optional requirements we implement

  • OptionalVersion control: GitHub, small branches, reviewable PRs. Repository made accessible to reviewers at the end.
  • OptionalCI: GitHub Actions builds and tests automatically and, on main, produces a Docker image artifact tagged with the commit SHA.
  • OptionalWeb interface: React UI on top of an ASP.NET Core Web API with CRUD for all three entities.
  • OptionalPersistence between restarts: SQLite via EF Core, Docker named volume mounted at /data.
  • OptionalContainerization: multi-stage Dockerfile and Docker Compose. API, database (SQLite file) and frontend in one container.
A-03

Deliberate deviations

  • OmittedCloud deployment (part of the optional CI/CD requirement): no Azure, no Neon, no registry push. The pipeline ends with a downloadable image artifact.
  • OmittedLogin and authentication (part of the optional web interface requirement, “accessible via login”). The UI is reachable without signing in.
  • Limited“Runnable locally and in the cloud”: the image is built to be cloud-ready (non-root, configuration via environment variables) but is only run and verified locally.
  • Limited“Build on each commit”: CI runs on pull requests and pushes to main. Commits on feature branches are built through their open PR.
A-04

Open domain questions

Decided together when the feature is built, then recorded with a date in the decision log.

  • PR 4 / 5Minimum cardinality: the challenge says “one or more”. Must an order have at least one board when saved, a board at least one component? Or are empty assignments allowed, for example as drafts?
  • PR 4 / 5Delete behavior with existing links: block, cascade, or remove only the link.
  • PR 3–5“One or more” for actions: bulk create, edit, search and remove. Scope, API shape and behavior on partial failure are open.
  • PR 3Search: which fields (Name, Description) and which matching (contains, case sensitivity)?
  • PR 3Validation: required fields, lengths, allowed range of Quantity (for example 0, or integers greater than 0).
  • PR 4Unit of Length and Width (millimetres are common in SMT) and data type (integer or decimal).
  • PR 5Order Date: date only or timestamp; default when creating.
  • PR 6JSON structure of the production download and file name.

Notes on our brief compared with the challenge

Quantity: the challenge puts Quantity on Component without defining its meaning. “Copies of this component per board” is our interpretation. As required, Quantity stays on Component even when the same component sits on several boards. We should state this interpretation explicitly in the presentation.

“One or more” applies to all four actions, not only removal. Our brief acknowledges this and rightly leaves the scope open for now.

Otherwise our brief neither contradicts the challenge nor misses a mandatory requirement.

T-02

Code conventions

The binding version lives in the repository: CLAUDE.md. This overview summarizes it; changes go through a PR to CLAUDE.md.

Backend

  • ProposedShared settings in Directory.Build.props: nullable enabled, warnings as errors, implicit usings.
  • Proposed.editorconfig as the single style source: 4 spaces in C#, 2 in TS/JSON/YAML, file-scoped namespaces, LF.
  • ProposedOne folder per feature (Features/Components with endpoints, DTOs and service). Endpoints registered via an extension method such as MapComponentEndpoints().
  • ProposedEntities are never exposed by the API; request and response DTOs are declared as record.
  • ProposedStructured logging with message templates ("Created component {ComponentId}"), no string interpolation.
  • Proposeddotnet format --verify-no-changes must pass locally; added to CI if needed.
  • ProposedTest names Method_Situation_ExpectedResult; // Arrange, // Act, // Assert comments in every test; NUnit constraint model (Assert.That), related checks grouped in Assert.EnterMultipleScope().

Frontend

  • ProposedLinting with ESLint (flat config in eslint.config.js): JS and typescript-eslint recommendations plus the React Hooks and React Refresh rules. npm run lint, npm run typecheck and npm run build must pass in CI.
  • ProposedAll API calls live in src/api/; components never call fetch directly.
  • ProposedNo UI library and no global state manager until there is a concrete need.

Git and language

  • DecidedNo direct commits to main; one branch per PR; PRs are merged by the project owner only.
  • DecidedEverything in English: code, comments, commits, README, CLAUDE.md, this handbook and project discussions.
  • ProposedBranch names feat/…, chore/…, docs/…, fix/…; commit messages in imperative mood with a short subject line.
